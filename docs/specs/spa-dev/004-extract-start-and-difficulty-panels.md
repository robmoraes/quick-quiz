# Feature: extract start and difficulty panels

## Intent

Problem: the topic selection and difficulty selection markup are large,
independent screen sections inside `IndexPage.vue`, but they still share the
same route and orchestration state.

Users or stakeholders:

- frontend maintainers;
- reviewers evaluating component composition;
- future contributors changing topic or difficulty UX.

Desired outcome: extract the first two selection screens into presentational
components while leaving API flow and screen transitions in `IndexPage.vue`.

Non-goals:

- change topic filtering behavior;
- change difficulty mapping or labels;
- introduce composables;
- change the visual design.

## Scope

In scope:

- create a start/topic selection panel component;
- create a difficulty selection panel component;
- pass all state through props;
- emit user intent through events;
- preserve current Quasar controls and styling classes.

Out of scope:

- extracting result, question, settings, rules, or ad screens;
- changing API calls;
- changing i18n messages;
- moving business logic into the extracted components.

Assumptions:

- `IndexPage.vue` remains the owner of selected topic, selected difficulty,
  loading, error, and session state;
- topic filtering may stay in `IndexPage.vue` for this step.

Dependencies:

- existing topic option and difficulty option shapes;
- existing i18n messages;
- existing styling in `src/css/app.scss`.

## Behavior

1. The start panel must show the same topic selector, topic description, rules
   button, error line, next action, and end-session action as today.
2. The difficulty panel must show the same selected topic summary, change-topic
   action, rules button, difficulty radios, difficulty banner, error line,
   start-run action, and end-session action as today.
3. The extracted components must not call the backend.
4. The extracted components must not mutate global or parent state directly.
5. User actions must be emitted with clear event names such as
   `next`, `end-session`, `open-rules`, `change-topic`, `start-run`,
   `topic-changed`, and `difficulty-changed`.
6. Disabled, loading, and error states must match the current SPA.
7. The topic select filtering behavior must remain unchanged.
8. The player must be able to complete the same path from topic selection to
   run start after this extraction.

## Acceptance Examples

### Scenario: topic selection continues to work

Given the player is on the start screen

When they filter and select a topic

Then the same topic options and description behavior appear

And clicking next opens the difficulty screen.

### Scenario: session end remains available

Given there is an open session

When the start or difficulty panel is visible

Then the end-session action is visible and behaves as before.

### Scenario: difficulty selection starts a run

Given the player selected a topic

When they choose an available difficulty and start the run

Then `IndexPage.vue` still performs the create-run API call

And the question screen opens as before.

- selected topic label and description;
- difficulty options;
- selected difficulty value and explanatory state;
- busy/loading/error flags;
- action labels generated by the parent.

Outputs:

- emitted UI events only.

API, schema, event, or CLI changes:

- none.

Persistence changes:

- none.

Machine-readable contract:

- not required.

## Quality Attributes

Security:

- no new data exposure.

Privacy:

- no new persistence.

Accessibility:

- extracted controls must preserve labels, aria labels, disabled states, and
  keyboard behavior.

Performance:

- component extraction must not add API requests or expensive recomputation.

Reliability:

- parent-owned state keeps rollback and partial refactor simple.

Observability:

- existing frontend events must continue to be emitted by orchestration code.
